# 9.36.7.15D — TLS PEAK PROBE

## Baseline

Source of truth: GitHub `main`. 15C hardware evidence is the baseline; do not modify JK/BLE, CAN, Wi-Fi architecture, OTA, or cloud write policy while investigating TLS.

Observed 15C failure:
- EcoFlow HTTPS GET returns HTTPClient code `-1`.
- `WiFiClientSecure::lastError`: `-32512`, `SSL - Memory allocation failed`.
- Immediately before GET: free heap about 38.7 kB, largest 8-bit block about 24.6 kB.
- Internal pre-TLS snapshot: about 28.8 kB free / 27.6 kB largest.
- Normal runtime later recovers to roughly 40–48 kB free and 24–30 kB largest8.
- Historical fragmentation reached largest8 1.46 kB; 15C materially improved this but did not make TLS succeed.
- Cloud worker completes; heavy-owner release mismatch is zero.
- JK/BMS has no observed drops/faults in the supplied run.
- Reset reason 6 and a loop max gap around 2240 ms remain a separate WDT/blocking investigation.

## Mandatory 15D scope

Diagnostic-only. No speculative functional fix in this revision.

1. Capture memory at each TLS phase using ESP-IDF heap capabilities:
   - total 8-bit free + largest
   - INTERNAL|8BIT free + largest
   - minimum free heap
   - before client construction
   - after client construction
   - after CA assignment
   - before/after HTTP begin
   - immediately before GET
   - immediately after GET/failure
   - after `http.end()` and TLS object cleanup
2. Distinguish transport stages explicitly: `NOT_TESTED`, `PASS`, `FAIL`; never encode `NOT_TESTED` as an apparent failure.
3. Do not run a throw-away TCP probe in the same request path if it perturbs the heap. Any DNS/TCP reachability probe must be isolated from the measured TLS attempt or executed as a separate diagnostic job.
4. Preserve fail-closed certificate verification. No `setInsecure()` fallback.
5. Preserve read-only EcoFlow cloud behavior. No PUT/write path is enabled by this diagnostic revision.
6. Record WDT/reset reason and loop-gap evidence separately from TLS memory evidence.

## Firmware / filesystem integrity gate

The filesystem regression seen during the 15C USB-package test is now a release blocker:
- Firmware and SPIFFS must be produced from the same Git commit.
- `data/fs_version.txt` must exist before `buildfs`.
- Its build ID must equal the firmware's expected filesystem build ID.
- CI must fail before publishing artifacts if the IDs differ or the manifest is missing.
- The UI must not present a filesystem-sourced version as the running firmware version.
- `FS_OK` means both mount/readability AND expected-build-ID match; otherwise return `FS_VERSION_MISMATCH` with expected and actual IDs.

## 15D acceptance criteria

15D is a diagnostic PASS even if EcoFlow TLS still fails, provided one hardware run can unambiguously distinguish:
- Wi-Fi/network reachability state,
- DNS/TCP test state without contaminating the TLS measurement,
- TLS handshake/allocation failure,
- total vs INTERNAL contiguous-memory pressure,
- cleanup/recovery after the failed request,
- WDT/blocking evidence as a separate fault domain.

No release promotion until firmware/SPIFFS provenance gate passes and existing JK/BLE, CAN, WebUI, Wi-Fi, OTA, cloud-worker lifecycle and read-only safety regressions remain green.
